# Distribution and Marketplace readiness

Checked against Elgato's official documentation on 28 October 2026. The current work is a development build for operator acceptance, not a Marketplace submission. Changes to the Stream Deck UI are expected after hands-on testing.

## Keep three independently updateable plugins

| Component | Install location/runtime | Role |
|---|---|---|
| Midi Fadester | OBS Studio 33 on Windows x64 and macOS 13.0+ | Optional integration that owns slots, MIDI control, filter bindings and the vendor API (0.6.0 release archives are Windows x64; macOS CoreMIDI builds from `main`). |
| Fadester for OBS | Stream Deck 7.6+ on Windows 10+ and macOS 13.5+ (and OpenDeck) | Provides dial/key controls, a Neo Info Bar display, VJster actions, and configuration. Updates independently of the OBS plugins. |
| Visual Sidechain | OBS Studio 33 on Windows x64 | Optional audio modulation, shader effects, and Tape Deck; can consume Midi's 18 slots or expose numeric filter settings for Midi to control. |

Use one coordinated setup guide and a tested compatibility matrix. An optional combined OBS installer could later offer Midi and Visual Sidechain as separate choices, but each plugin should keep independent versions, uninstall behavior and downloads. Do not bundle OBS binaries into the Stream Deck plugin. Keep the two OBS components optional for users who need only one. For Stream Deck users, clearly disclose that Midi Fadester is optional for the main OBS controls and required for its two optional actions; Visual Sidechain is optional.

Retain the existing plugin/action UUIDs within each edition (the Marketplace's and the GitHub download's differ since 0.10: see "The Elgato Marketplace edition"). Use a new package version when publishing an update; do not change identities to distribute a revised implementation. Keep development packages off Marketplace until the operator signs off on real hardware behavior.

## Operator acceptance before submission

- Test on the actual Stream Deck +: rotation, fine/coarse steps, short press, hold, touch rails, and immediate/timed keys. Specifically confirm that zero aborts a partial T-bar throw and Finish commits it.
- Test the Neo Info Bar on a real Stream Deck Neo, including scene changes, Studio Mode changes, disconnection, and reconnection. Confirm the display stays readable with long scene names.
- Confirm Clean FX resets enabled filters in either bank, leaves audio/opacity/A/B controls unchanged, and handles missing/re-added filters. Check custom All FX labels and mapped units.
- Configure a slot entirely in the inspector; test partial ranges, full-range reset, enabled state, calibration, save/reopen, rapid source changes and catalog failures. Pending edits must stay intact.
- Exercise wrong password, disconnected OBS, reconnect and Midi 0.3 compatibility. Confirm the exact required OBS/Stream Deck versions and Windows support in the listing.
- Load a controller profile only in a disposable test setup: it replaces all slot assignments. Keep unsupported physical controllers marked Beta.

The browser harness and automated suites help catch regressions but do not replace this device pass. Live OBS automation for this workspace must use the approved Midi `scripts/run-live-selftest.ps1` wrapper; do not run the older separate-root conformance script.

## Packaging and submission

Run `npm test`, `npx tsc --noEmit`, `npm run build`, `npm run validate`, and `npm run test:mutation`, then `npm run pack`. Packaging produces a `.streamDeckPlugin` file; it does not publish or install the plugin. Elgato's CLI validates and bundles the `.sdPlugin` directory. [Official distribution guide](https://docs.elgato.com/streamdeck/sdk/introduction/distribution/).

Review the plugin metadata, names, icons, feedback and inspector behavior. Action settings should save on change; the explicit Apply control here edits a shared OBS configuration, not the action's saved settings. Confirm readable touch targets, validation feedback, and action-list icon styling before submission. Ensure the manifest Author matches the chosen Maker organization. [Official plugin guidelines](https://docs.elgato.com/guidelines/stream-deck/plugins/).

Prepare the package, name/description, release notes, support/setup links, a 1920×960 PNG thumbnail, and three gallery items using the required image/video formats. Register/sign in to Maker Console, choose **Create product → Stream Deck plugin**, upload, complete the listing, and submit for Elgato review. Choose the product name and monetization deliberately because those are not freely editable in Maker Console. No account, agreement, upload or submission is performed by this integration task. [Official submission guide](https://docs.elgato.com/maker-console/submitting-products/).

Use screenshots from the final approved UI and real hardware, not the fake-server harness as evidence of device verification. Keep a public setup/troubleshooting page explaining how to enable OBS WebSocket and connect, and how to install optional Midi Fadester and Visual Sidechain integrations. Publish only after the operator has approved the hardware pass and Elgato has completed its review.

## The Elgato Marketplace edition

The Marketplace product has had the ID `com.jbrick2070.fadester-for-obs` since 0.8. Every other download (GitHub, Suite Setup, OpenDeck) has been `io.github.jbrick2070.fadester-for-obs` since 0.10, because the OpenDeck catalogue asks for an ID on a domain the author controls. Maker Console refuses a package whose ID is not the product's, and Stream Deck stores a person's keys under the plugin's ID, so an update on the Marketplace must keep the old one. The two editions are the same code and the same nineteen actions.

`npm run build`, then `npm run pack:marketplace` (`scripts/suite/package-marketplace.ts`) writes `release/marketplace/com.jbrick2070.fadester-for-obs.streamDeckPlugin` and `MARKETPLACE.json` (version, checksum). The script copies the built plugin folder, writes the Marketplace ID into every file that names the other one (the manifest, the code, the settings pages, the language files, the layouts and the actions inside the fourteen profiles), and stops unless: no file names the other ID any more; every action that a profile's key, a language file or the built code names is one of the manifest's nineteen; the suite's seven VJster actions are among them; and the ten actions of 0.8 are all still there (a key placed with 0.8 must find its action after the update). A file that does not name the ID is copied byte for byte. Elgato's own tool then validates and packs it. Nothing is installed, uploaded or published.

Both workflows pack it and start it as Stream Deck does, on Windows and on macOS: `streamdeck-cross-platform.yml` on every pull request and push (artifact `Fadester-for-OBS-Elgato-Marketplace-<platform>-<arch>`, kept 3 days; a fault there fails the pull request's check, on purpose) and `release.yml` on a tag (artifact `marketplace-fadester-for-obs-<platform>-<arch>`, kept 30 days; a job of its own that runs after the tag check and the tests of the GitHub package, and that the draft release does not wait for, so a fault in this edition never holds back the GitHub release). It is never attached to the GitHub release: two editions of one plugin would be offered side by side there.

For an upload: check in Maker Console which version and ID the product has today; use the tag's Windows artifact; **Create version**, upload the file, write the release notes from `CHANGELOG.md`; the listing's pictures and video must show this version's window. Publishing there is the owner's word, as every release is.

Known limits. Stream Deck holds the two editions as two plugins: a computer should have one of them (README, "When something is off"). With both, their VJster parts also contend for port 48150. Suite Setup looks for the Marketplace edition: beside it, it offers no copy of its own and says so, and where both are there already it says that one should be removed (`installer/README.md`). The Marketplace edition is for Elgato's Stream Deck software only; OpenDeck gets the other ID.

## Version numbers at a release

A tag `vX.Y.Z` releases Fadester for OBS X.Y.Z; `package.json` and the plugin's `manifest.json` must say the same (the release workflow checks it). Fadester Suite Setup carries that number too: `installer/build-suite.ps1` reads it from `package.json` (up to 0.12.16 the setup was named by its build date). Two other things are attached to every release under versions of their own, and the workflow's job **Companion and VJster extension versions moved with their code** (`scripts/release-component-versions.mjs`) stops a tag that changed one of them without raising its number. Each is compared with the release that first carried its present version:

| Component | Raise | When any of these changed since that release |
|---|---|---|
| Fadester Companion | `components.companion.version` in `installer/components.json`, and what the tests keep equal to it (`tourbox/macos/panel/Info.plist`; `tests/companion-one-name.test.ts` names the rest) | `tourbox/`, `vjster-page/`, `src/vjster/shared/`, and the three files of `vjster-extension/src/` the OBS page is built from (`adapter-core.ts`, `link-client.ts`, `page-state.ts`) |
| VJster Chrome extension | `version` in `vjster-extension/manifest.json` | `vjster-extension/`, `src/vjster/shared/` |

Release 1.5.0 (20 November 2026, branch `release/1.5`) was the suite-wide step: every product in this repository went to 1.5.0 at once, with Midi Fadester and Playlister, so that one round of hand tests covers them all. The second and third passes before it had changed the Companion and the extension and raised neither, on purpose. After 1.5.0 each product keeps a version of its own again: a release always raises Fadester for OBS (and Suite Setup with it), and the others when the table above says so (the standalone VJster plugin: when `com.jbrick2070.vjster.sdPlugin/` or `src/vjster/` changed). Do the step in this order; each line names every file that holds the number.

1. **Fadester for OBS and Fadester Suite Setup** (the tag's number, `X.Y.Z`):
   - `package.json` (`version`), then `npm install --package-lock-only` so `package-lock.json` follows (two lines change and nothing else);
   - `io.github.jbrick2070.fadester-for-obs.sdPlugin/manifest.json` (`Version`, as `X.Y.Z.0`);
   - `README.md`: the first paragraph (**Fadester for OBS X.Y.Z**) and the example foot line under "Then, if you like" (`Fadester for OBS X.Y.Z · Connected to OBS …`);
   - Suite Setup has no file of its own to edit: its file name (`Fadester-Suite-Setup-X.Y.Z-Windows-x64.exe`), its version in Windows **Installed apps** and its wizard follow `package.json`.
2. **The standalone VJster plugin**: `Version` in `com.jbrick2070.vjster.sdPlugin/manifest.json` (four parts), then `node --import tsx scripts/vjster/build-profiles.ts`: its four bundled profiles hold the version, `npm run build` does not rebuild them, and `tests/vjster-plugin-package.test.ts` calls them stale until that script has run. Then the number in the first line of `docs/vjster/README.md` (**VJster A.B.C**) and in `docs/vjster/TESTING.md` ("… `manifest.json` (A.B.C.0 today)"). The plugin is not attached to this repository's releases, so no job checks its number.
3. **The VJster Chrome extension**: `version` in `vjster-extension/manifest.json`. Nothing else holds it. (`components.vjsterExtension` in `installer/components.json` is not this number but a pin: see step 8.)
4. **Fadester Companion**: `components.companion.version` in `installer/components.json` and `CFBundleShortVersionString` in `tourbox/macos/panel/Info.plist`. `tests/companion-one-name.test.ts` fails when the two differ. Every build reads the number from `components.json`: the Windows ZIP (`tourbox/build.ps1`), the installer Suite Setup runs (`installer/build-suite.ps1` compiles `FadesterCompanion.iss` with it), the Store package (`tourbox/store/make-msix.ps1` puts it, as `A.B.C.0`, in place of `$VERSION$` in `AppxManifest.xml`; a `-Version` passed to the script wins, and both workflows pass that same number) and the Mac app (`tourbox/macos/panel/build.sh` writes it into the built app's `Info.plist`). Not raised, because no window shows them: the 0.1 in the `Info.plist` of the Mac helpers (`tourbox/macos/native/`, `input/`, `probe/`, `write-probe/`) and the 1.0.0.0 in `tourbox/panel/app.manifest`. The Microsoft Store listing names the version it was written for: the line under **What's new in this version** in `tourbox/store/LISTING.md`, and in `tourbox/store/LISTING-translations.md` the first paragraph and each language's **What's new** line (thirteen places). The sentences under those lines are that version's news for a Store reader, so they are written again with the number, in all thirteen languages: from the changelog's **Fadester Companion and Suite Setup** part, in the Companion's own words for its buttons and lights (`tourbox/panel/PanelText.cs`, `PanelExtraText.cs`), 1,500 characters at most per language (Partner Center's limit for that field), and with none of the verbs `tests/companion-take-verbs.test.ts` lists (it reads both files). The notes for certification in `LISTING.md` name buttons and steps of the window: read them against the new window too.
5. **Refresh the copies**: `npm run suite:assemble`. It rewrites `assets/manifest.json` (a copy of the Fadester manifest) and `io.github.jbrick2070.fadester-for-obs.sdPlugin/vjster/manifest.json` (a copy of the VJster manifest); until it has run, `tests/suite-assemble.test.ts` reports both as different. Then `npm run build`, which also rebuilds the fourteen bundled profiles of Fadester for OBS (they hold the version too, so all fourteen change and are committed).
6. **The changelog**: the **Unreleased** heading in `CHANGELOG.md` becomes the new version and date, with its first line saying which Companion and extension versions the release ships; a new, empty **Unreleased** goes above it.
7. **Check, then commit, then check the versions**: `npm test`, `npm run build` and `npm run validate` on the edited files. Commit steps 1 to 6. Only then run `node scripts/release-component-versions.mjs`: it reads the committed files (`HEAD`), not the working folder, so before the commit it still reports the old numbers and stops. It needs the whole history and the release tags. A working clone made a few commits deep is shallow (`git rev-parse --is-shallow-repository` says `true`) and may fetch no tags: then first `git fetch --unshallow --tags` (on a full clone: `git fetch --tags`). The script refuses a shallow clone: with the tags fetched and the history cut, no tag counts as an earlier release and both lines would read "a version no earlier release carries" whatever the numbers are. Both component lines must start with `ok`, and there must be no `note` line (it means no tag was found at all).
8. **After the releases are published**, not before: `node installer/update-pins.mjs …` downloads each published file you name and rewrites its `version`, `file`, `url` and `sha256` in `installer/components.json` (`--sd` for `fadesterForObs`, `--ext` for `vjsterExtension`, `--midi` for `midiFadester`, `--playlister`); it changes no other file. `--ext` also needs `--ext-tag <tag>` or `--sd`, which say which release holds the extension's zip; without one the script stops. For 1.5.0 it went in two steps: Midi Fadester 1.5.0 and Playlister 1.5.0 were published first and `node installer/update-pins.mjs --midi 1.5.0 --playlister 1.5.0` ran before the tag, so the release's setup carries them; once this repository's v1.5.0 was published (a draft cannot be downloaded), `node installer/update-pins.mjs --sd 1.5.0 --ext 1.5.0` moved the other two. After the script, edit `installer/README.md` by hand in two places: the example command under **Shipping a new plugin version**, and the versions named under **Pins wait for publication**. Commit both files; the pull request runs the Suite Setup workflow on the new pins.

What the four pins are, until step 8 has run: the labels and hashes of the last *published* files. `midiFadester` and `playlister` decide what every Suite Setup carries, because those two installers are never built here: a setup built from a commit holds the Midi Fadester and Playlister that commit's pins name. So the setup attached to a release is as new as the pins of the tagged commit; for a setup that carries a new Midi Fadester or Playlister, publish those two first, move their pins, and tag after that. `fadesterForObs` and `vjsterExtension` are different: the workflow builds both from the commit (`-Candidate`), so their pins only serve a build by hand without `-Candidate` and the checksum test of `installer/tests/Test-Suite.ps1`, which downloads all four pinned files. That is why `vjsterExtension` could stay at 0.1.3 (release v0.11.0) while the extension went on to 0.1.6, until release 1.5.0 moved it, with no wrong file in any release. A release that a pin points to must stay published, or that test and every build by hand fail.

Version numbers that are floors, not the current version, stay as they are unless the requirement itself changes: "VJster 0.2.1 or later", "Fadester for OBS 0.11.0", "Visual Sidechain 0.6.0" and "Stream Deck 7.6" in `demo-kit/README.md` (the phrases `demo-kit/kit_docs.py` `README_MUSTS` requires there, so change both together), "Fadester for OBS 0.12.14 (or later) and VJster 0.2.1" in `demo-kit/TESTING.md`, "Midi Fadester 0.9.0 or newer" in the plugin's texts, "Fadester for OBS 0.9.0 or later" in VJster's guides, "Playlister 0.5 or later" for the Playlister keys, and the tag in the example of `.github/workflows/suite-installer.yml`. A floor is raised only where a feature needs it, and then for that feature alone: the names of the playing and the next item on the Playlister keys need Playlister 1.5.0 or newer (its `get_now_next` request), and `README.md` and `DECK-LAYOUTS.md` say so beside the 0.5 floor, with what an older Playlister shows. The version numbers inside `tests/release-component-versions.test.ts` are a pretend history and never change.

To see what a tag would say before pushing it: `node scripts/release-component-versions.mjs` (it needs the whole history and the release tags, see step 7, and it reads the last commit, so commit first; `node scripts/release-component-versions.mjs <commit>` checks another commit).
